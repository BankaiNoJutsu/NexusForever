## Ownership and acknowledgement

`QuestRowPersistence` owns copied scalar baselines, dirty-field revisions, the current context and known uncertain candidates. It records the last successful flush independently of the last staged snapshot. Only a committed terminal result acknowledges that flush. Later mutations, including touching the same value again, retain their new revisions. Suppressed, failed, disposed or rolled-back units keep intent. Lost acknowledgements and savepoint rollback reconcile through a fresh context against complete known candidates. Restaging without another flush cannot acknowledge new progress.

Each row has process-local database/key ownership. A shared database/character/quest scope also orders parent and objective units, including direct objective saves. Another loaded owner cannot join the row in the same context or overlap it in another context. A failed partial enrollment permanently rejects the shared context. Baseline checks reject foreign root/objective state; tracked snapshot/original/state/modified-field guards run before SQL, and explicit commits read the owned SQL state back after the last flush. Existing objective ordinal0 binds explicitly as an unchanged composite-key row instead of relying on EF Attach's generated-key inference.

Quest and objective masks no longer clear when staged. PendingCreate distinguishes a never-staged create from one already attempted, so abandonment after an in-flight create cannot discard a necessary deletion. Parent deletion dominates objective writes. Canceling an unflushed or flushed deletion can restore the complete graph, including after a cascade or later rollback. The original and absent objective candidates remain available for fresh reconciliation. Parent settlement propagates known absence to objective baselines without resurrecting a still-deleted quest.

SQL callbacks publish deletion acknowledgements into a protected set. Actor reads/ticks remove only the matching old object while its deletion is still intended; a replacement or reaccepted quest cannot be retired by an older acknowledgement. Pending deletions stop ticking their quest timers and cannot emit a false failure while waiting for SQL.

Reset values preserve provider conversion. The current MySQL/MariaDB mapping uses DATETIME without fractional precision. Staging asks that SQL session to cast the original value, rather than imposing a rounding or truncation policy. Settlement uses captured conversions without querying a disposed context. The regression compares the result with a direct EF write of the same timestamp; SQLite retains its own precision. No schema or migration changes were made.
