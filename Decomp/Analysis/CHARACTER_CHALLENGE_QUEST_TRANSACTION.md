## Snapshot and SQL boundary

`CharacterChallengeQuestChanges` copies root state, flags, timer and reset plus every objective's index, progress and timer. Collections are copied, sorted and read-only; no EF entities, Quest objects, scripts or callbacks cross onto the SQL worker. A bundle can attach only to a terminal Medal/Finish command that increments completion once. Duplicate quest IDs, foreign owners, ambiguous objectives and changed identities are rejected. Empty before/after graphs represent actual creation/deletion, so future actor capture can retain script-driven graph changes instead of reducing completion to a counter.

The existing serializable Character owner lock orders the reward and participants. Each complete before graph must match SQL before any participant is staged. Root/objective additions, modifications and deletions join the medal/attempt/Challenge writes. Existing and new objective ordinal zero bind as explicit keys; a temporary generated key cannot replace the captured ordinal. MySQL reset values use that SQL session's DATETIME conversion, compared with a direct EF reference rather than an invented rounding rule.

Existing tracker/original/scalar ownership checks now also handle committed deletion correctly. Explicit commit reads every staged row and every complete resulting graph back from SQL. Added or missing untracked objectives therefore invalidate the whole transaction. Late tracker changes, suppressed writes and raw SQL changes cannot commit only the medal or only part of the Quest graph. Failed units roll back together.

Replay never sends a broad CompleteChallenge event. A present receipt/terminal marker requires the exact after graph and performs no new mutation. An absent reward during uncertain-outcome reconciliation requires the exact before graph. A later quest edit or abandonment/reacceptance conflicts instead of receiving another increment. Existing retained executor proofs still bind command identity and terminal ownership. These SQL values do not establish an acceptance identity when two quest instances happen to have identical scalars; actor ownership remains necessary.
