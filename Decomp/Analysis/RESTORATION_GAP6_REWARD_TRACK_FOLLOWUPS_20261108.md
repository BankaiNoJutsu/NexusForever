### 1c. New correction to pass 2 (agent-written, frames viewed by this agent)
Pass 2 states that the PTR values are "a factor 10 below the 16042 tables twice" (threshold 600000 vs 6000000, and the claim's 2 Platinum 50 Gold, 2,500,000 copper, vs 250000). The currency half is the opposite direction: 2,500,000 is **ten times higher** than row 535's 250,000, not lower (client Lua `CraftingGrid.lua` 1176-1183 formats copper as platinum = 1,000,000, gold = 10,000, so 2p50g = 2,500,000). I also re-viewed clip AyXyE6qWnMU: at 795 s the chat tail (all stamped 20:27) is Elder Points, Bonus Signature, Rest Elder Points and "6 Elder Gem" with no pouch and no money; at 834 s the same block additionally ends "You receive [Icebound Pouch]" then "You receive 2 Platinum, 50 Gold", and the click on the crown happened at about 806 s. So the pouch and 2,500,000 copper were appended by the claim (Observed), not by the quest turn-in at about 789 s as pass 2 allowed. Result: the preview differs from the 16042 row 535 on both numbers, in opposite directions (points x10 up in the table, credits x10 down in the table). A single "preview rescale" does not explain both; two digit-shifted values could also be a transcription or tuning difference, but that is speculation. 2,500,000 equals the Contract final credits (rows 69 and 270), which fits a copy of the Contract final reward template in the preview.

## 3. Public 07CE: what the packet needs and what evidence exists
### 3a. Packet and client facts (existing records, repeated for the decision)
- `ClientRewardTrackClaimRewardPoint` (07CE) carries only `RewardTrackRewardsId` (14 bits) and `ChoiceIndex` (uint). There is **no cycle nonce, track id or claimed-state echo**, so the server must derive owner, cycle, claimed mask and choice validity from its own state ([CONTRACT_REWARD_TRACK_IMPLEMENTATION.md](CONTRACT_REWARD_TRACK_IMPLEMENTATION.md)). The current `ClientRewardTrackClaimRewardPointHandler` routes only type 2 (Loyalty) and type 3 (Challenge); it has no type 0/1 (Contract) or 4 (Zone) case, while `ClientRewardTrackChooseTrackHandler` (07CF) already routes 0/1.
- Choice policy: player-selected, index into the reward's choice list (zero-based most likely; helper not read), all offered choices shown, claim enabled only when `bCanClaim and not bIsClaimed`, direct claim when there are no choices ([CLIENT_LUA_CONTRACT_AND_REWARD_EVIDENCE_20261107.md](CLIENT_LUA_CONTRACT_AND_REWARD_EVIDENCE_20261107.md)).
- Final-first claimability: native `RewardTrack_CanClaimRewardPoint` (1404d2240) checks the position's claimed bit and cumulative cost only; Lua has no "claim earlier first" rule. The Observed 2017-05-18 clip is consistent (two ready milestones, one visible as claimable ahead of the other in the panel).
- Packet replacement: `07D5` handler `1404d18e0` overwrites progress, claimed mask and unlock wholesale and the Contracts UI redraws on a lower value, so a server reset can be expressed by sending a lower total and a cleared mask ([CONTRACT_RETAIL_RESET_EVIDENCE.md](CONTRACT_RETAIL_RESET_EVIDENCE.md)).
- Table side: Contract tracks 4/5 have 242 rows and 726 canonical choices (486 Item2, 240 account currency, six final credit awards); `Do not expose a partial set of 726 choices or use synthetic item/stacking metadata as full-table delivery evidence` stands ([ASSESSMENT_REMAINING_WORK.md](ASSESSMENT_REMAINING_WORK.md) queue item at line 3044).

Therefore the reset/unclaimed/excess policy for 07CE types 0/1/3 is an unresolved inference: the only footage-backed rule ("subtract one threshold at claim time, keep the excess") is for type 4, the one type the server does not implement and whose scale (section 1) is itself unresolved. Do not generalise it to Contract tracks.

## Recommendation (conservative)
1. **No server change is supported.** Keep type 4 (zone) earning and claims disabled, keep public 07CE unwired for types 0/1, keep the current type 2/3 routing. Do not alter row 535 or track 35 values and do not infer 600,000.
2. Do not enable any partial 07CE: Contract claims need the full 726-choice delivery gates and a reset policy that has no retail witness. The working direction recorded in `CONTRACT_RETAIL_RESET_EVIDENCE.md` (reset after successful final-reward collection) remains an inference from one forum remark plus final-first claimability, not a Mapped rule.
3. If type 4 is ever implemented, the evidence-backed shape is: client-initiated claim of the single milestone, subtract one threshold from the running total at claim, keep the excess, loot messages for the item (and the currency amount only once the 250,000 versus 2,500,000 question is settled). The currency amount and the threshold are the two disputed constants; use the 16042 table values until a retail post-launch clip or a native read of the `nCost` path says otherwise.
4. Evidence still worth obtaining, in priority order: (a) the native read of `nCost`/`GetRewardPointsEarned` scaling above; (b) any retail clip, dated before 2018-11-28, that reopens the Codex Challenge Log or the Zone map panel after claiming the last milestone; (c) a Basic and Signature pair on the same tier. The corpus work for (b) is exhausted for the Arcterra-titled uploads (the two 2018 LMC clips never open the track panel).

## Lead review and native read (2026-11-08)
Not re-derived: the agent's clip readings and table values. Done by the lead: the requested read of `Lua_RewardTrack_GetAllRewards` (`1406ba350`, registrar `1406b9550`, class `Game.RewardTrack`).
* The `nCost` field of each reward entry is `iVar8 = *(int *)(*(longlong *)(track + 0x10) + index * 4)` (bounds-checked against the count at `track + 0x18`) pushed as `(double)iVar8` (decompiled lines 745 to 779).
  It is the track object's own integer array, passed through **with no scaling**. `ZoneMap.lua` 1518 to 1543 prints `nRewardProgress` (`GetRewardPointsEarned`) over that raw `nCost` and uses it as the progress bar maximum.
* So the denominator the final client shows is the table threshold as loaded: 6,000,000 for track 35 in the 16042 tables. The 600,000 in the three February to March 2016 clips is therefore a threshold in the
  data those builds loaded (a pre-launch table), not a display scale of this client. The numerator (`GetRewardPointsEarned`) is covered by [REWARD_TRACK_POINTS_NATIVE_READ_20261108.md](REWARD_TRACK_POINTS_NATIVE_READ_20261108.md).
* Limit: this is one accessor plus the Lua that prints it; the array's fill path (where the integers are copied from the table row) was not read. No post-launch footage exists, so 6,000,000 is the shipped value by table, not by video.
* Effect on the server: using the table threshold unscaled matches the client's reading. This answers the scale question for the denominator only. The zone-track earning producer (type 4 point amounts for public events, quests, kills)
  remains unwitnessed, so type 4 and public 07CE stay disabled; no code change.
