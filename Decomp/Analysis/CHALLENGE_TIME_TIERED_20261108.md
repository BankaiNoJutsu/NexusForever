# Time-tiered challenges: what is known and the exact missing input (2026-11-08)

Goal: [VIDEO_WITNESS_GOAL_PROMPT.md](VIDEO_WITNESS_GOAL_PROMPT.md), next-queue item 1; follows divergence 2 of [VIDEO_WITNESS_CHALLENGE_TIERS_20261108.md](VIDEO_WITNESS_CHALLENGE_TIERS_20261108.md).
Evidence tier: **native read + table census + dated retail footage (Observed)**. **No code changed**: the slice is blocked on per-challenge data that exists in none of the tables or the client, see Gate. No retail parity claim.

## Established
- **Flag.** `Challenge:IsTimeTiered` (binding `FUN_140685950`) returns `(ChallengeEntry.ChallengeFlags >> 3) & 1`, i.e. flag bit `0x8`, the same bit the server already names `TimeTieredFlag` (it only uses it to exclude durable producers, `ChallengeManager.LiveRewards.cs:19`). The table has **80** such rows (66 type General, 5 type 0, 5 type 7, 3 type 5, 1 type 1); tier-slot counts 3 (60 rows), 1 (14), 2 (6); the first goal is 0 in 61 rows and 1 in 10. Of the 72 rows with a goal of 1000 or more, 69 carry the flag; the three exceptions (Elemental Purge 423 and 1115 with [0, 30000, 60000], Dummy Damage 499 with [5000, 10000, 20000]) are not flagged and their goals are probably real counts or scores (unresolved).
- **Rule.** `ChallengeDisplay.lua` (extracted from the installed client): a time-tiered tier is kept while `elapsed < TimeLimit - TierGoal`, i.e. each tier goal is the **minimum remaining time in ms** at completion, and the first tier's goal is 0 or 1 ms (finish inside the limit). So the tier at completion is the highest tier whose goal is at most the remaining time.
- **Where the limit comes from.** `Challenge:GetDuration` (`FUN_1406863e0`) returns state word `+0x40` times a ms to s scale, that is the packet's `TimeTotalActive`; `GetTimer` reads the running counters from the same row. **The per-challenge time limit is therefore server data sent in the update packet, not a table or client constant.** `Challenge.tbl` has no column that holds a limit (checked the rows of Flitterfly Chaser, Thayd Sprint and Might as Well Jump), and `ChallengeTier.tbl` holds only the goal.
- **Footage (dated retail, 2014-06-05, `Wildstar Challenge： Thayd Sprint - Without mount guide`).** The 2014 widget counts down from about 2:00 (01:55 at 6 s, 00:58 at 60 s of the video) with the threshold list `:00 / 1:00 / 1:10`; the run finishes with roughly 0:56 left, which by the rule above is Bronze only. So Thayd Sprint's limit is **120 s** (Observed), against the server's fixed 300 s for every challenge (`DefaultActiveSeconds`). The 2014 HUD differs from the final-build addon (the list is static there), so only the limit and the goal values are taken from it, not the rendering.

## Server today
All challenges get `DefaultActiveSeconds` (300) as `TimeTotalActive` and `ActiveTimer`; `GetTierGoalCounts` drops zero goals and `TryAdvanceProgress` accumulates counts toward a tier goal. Nothing in `ChallengeProgressHooks`/`ChallengeCombatHooks` produces progress for a General sprint or climb, and durable producers already exclude flag `0x8`. So a time-tiered challenge cannot currently reach its second or third tier, and a first-tier goal of 0 shifts the other tiers down one place.

## Gate (exact missing input)
Implementing the rule needs, for each of the 80 flagged challenges, (1) the retail time limit and (2) the completion trigger (what makes a sprint, climb or race complete). With only the 300 s default, thresholds of 60 to 70 s would make Gold trivial for Thayd Sprint, so guessing would be worse than the current state. Footage census: of the 69 named flagged challenges, **18** have dated retail footage hits (title or subtitle): Back to Basic, Bringin' the Bingberries, Diabolic Drift Dash, Doing Things The Hard Way, Entrance Exam, Grounding the Storm, Powering Down, Race to the Top, Race to the Unknown, Rock Climber, Stairway to Heaven, Thayd Sprint, The Grid, To the Roof, Top of the World, Treeclimber, Windrunner, Windwalker; the other 51 have none in the indexed library.

## Harvest result 1: Back to Basic (dated retail, 2015-01-25)
`_Additional/Wildstar - Challenge - Back to Basic - Gold [...].mp4` (uploaded 2015-01-25, 960x720, title says Gold). Challenge 956 "Back to Basic" has goals **0 / 18000 / 25000** and the widget's threshold list reads `:00 / :18 / :25` (an exact match, in ascending Bronze, Silver, Gold order with red, grey and gold icons). The countdown is first visible at **01:04** (video time 48 s; hidden at 47 s) and runs 01:02 at 50 s, 00:52 at 60 s, 00:42 at 70 s, 00:36 at 76 s, 00:30 at 82 s; the card "Back to Basic Complete!" appears by 86 s, still with about 25 to 29 s left, so the finish is at or above the 25 s Gold goal, matching the uploader's title and the minimum-remaining rule. **Observed limit about 65 s** (the widget could hide the first one or two seconds), against 120 s for Thayd Sprint (2014-06-05) and 300 s for the server's default. So limits differ per challenge, as the packet-supplied `TimeTotalActive` implies.

## New retail witness: the challenge reward chooser (lead for 5b, not part of this slice)
In the same video (about 96 s) the completion card shows four loot icons labelled "Best Odds", "Average Odds" and "Good Luck!" each with "10x", and the text "Increase the chance of getting that item by 10x!" for the Gold finish (the 2013 beta stream showed "2x"; the multiplier therefore likely depends on the tier). The server defines no reward-list or reward-choice message (only `ClientChallengeChoice` and the Update/Result/Shared/ShareTimeout packets), while the client addons handle `ChallengeRewardListReady`. This is the first dated retail evidence of the chooser and is recorded as goal item V8.
