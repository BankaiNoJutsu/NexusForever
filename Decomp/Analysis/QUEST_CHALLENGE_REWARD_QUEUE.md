## One queue and one command

A queued request can retain its immediate actor-owned Quest census alongside copied Challenge intent. A capture can be submitted only once, by the same Player, after its preceding captures have joined that same queue. Out-of-order or cross-queue submission rejects before taking ownership; it does not consume the capture, so correct ordering remains possible. An earning completion cannot combine with an item-claim reservation. The capture's database must match the queue's retained execution database before a SQL probe starts.

The queue retains its save-blocking ticket and Quest character scope while waiting for normal inventory ownership, identity work or a Challenge uncertain-baseline load. The actor builds the command from the resolved Challenge baseline. The Quest probe copies its FIFO-head baseline candidates and frozen completion graph; only immutable scalar input crosses to its worker. The resulting participant changes attach to one exact terminal Medal/Finish command. The Challenge lease executes that same command, and the Quest capture watches the same task/result. There is one write unit for reward receipts, Challenge state and exact Quest graph changes. Recovery resumes that exact command through both owners, without rebuilding intent or invoking the broad objective event again.

Challenge adoption preflights baselines and runtime merge first. Quest adoption then validates every frozen participant and current owner before acknowledging either aggregate. The Challenge update and Quest acknowledgement run synchronously on the actor while both owners remain retained. Only matching captured revisions become clean; later Challenge counts/timers/share timers and Quest values remain dirty. Queue publication follows successful adoption of both, with its ticket still held. Any rejection quarantines both and suppresses publication.

Cancellation covers pending captures, identity work, the Quest read probe, normal-save waits and write units. An event already run requires authoritative reload even if no reward SQL starts. Invalidation during a write keeps both owners until genuine terminal proof. Both final-disposal tails reference the same operation; they may release dead-owner bookkeeping without event polling, but cannot adopt late actor values or publish UI. Unknown original units remain pinned. A throwing publication callback cannot reopen committed SQL or either completed capture.
