## Request and publication contract

The character manager accepts requests only with a concrete inventory capability, no pending save/reward operation or reload requirement, and its exact committed snapshot actually included in a full reload. Presentation now retains an opaque snapshot identity separately from accepted contributions. A character contribution waiting for account readiness, or accepted with reload=false, cannot authorize a new cycle. Account full reloads bind the character snapshot they actually contain. Reentrant sends bind the last full packet enqueued, including when a newer contribution was accepted without sending. Invalidation clears the binding. No owner callback is invoked under the presentation lock.

Choose captures satisfied prerequisites and the complete set of persisted track revisions on the actor, then queues the immutable command. The repository serializes selection and initializes a missing supported cycle once. Selection never changes a Challenge's earning owner. All sixteen complete catalogs are supported; the five empty catalogs remain explicit fallbacks.

Claim validates the published track/cycle, exact selected ordinal/row, claimed bit, earned points, canonical choice and current eligibility before preparing inventory. It forwards capacity failures through the existing inventory error. The retained command freezes cycle/revision, choice, claim identity, time and satisfied prerequisites. The queue/repository then commit forced-bound Items, receipt and claimed/reset state together. Actor publication follows authenticated commit; failed or uncertain operations use the established recovery/reload rules. A foreign revision/winner cannot allocate a local replacement award. Repeated requests for an already claimed slot do not regrant inventory.

07CE contains a reward row and choice but **no cycle nonce**. The explicit policy is to bind each accepted packet to the latest character snapshot actually published. A delayed old packet with a row also selected in a new cycle cannot be distinguished from a new request for that row; this implementation does not invent that guarantee. Final-first claiming remains allowed. After all slots are claimed the declared server policy subtracts the maximum once, carries excess and persists the next selection. A repeated static row in the next cycle gets a new durable receipt identity. This policy is not a recovered retail reset/RNG claim.

Every committed mutation republishes the character contribution through the composed account/character coordinator. Type2 Loyalty keeps its durable owner. Its registered-handler fixtures now supply the injected table dependency and a correctly bound world session; their durable pending-item and active-track assertions are retained.
